Anything past/further-out gets an honest "can't see that far" reply instead of a guess. — `93b4a3d`
- **Lockdown mode**, after two design pivots:
  - v1: PIN-gated via a native popup, DPAPI-encrypted credential storage. Built, tested with mocks — failed live twice. Root cause: `SetForegroundWindow`/`SetFocus` can't reliably be called from a background thread on Windows (foreground-lock restriction). Fixed that with `AttachThreadInput`, but voice-triggered activation stayed unreliable. Abandoned.
  - v2 (shipped): no popup, no stored credential. Engage with **"lockdown"** / **"lockdown protocol"** / **"engage lockdown"** — bare trigger. Disengage with **"unlock fred 1111"** / **"lift lockdown 1111"** / **"stand down 1111"** — PIN said together with the phrase, checked as a plain constant in `system_tools.py` (`_LOCKDOWN_PIN = "1111"`, demo-grade, not a real secret). Works spoken or typed into the HUD textbox — both hit the same dispatcher.
  - While locked: every tool call refused at the single choke point (`ToolRegistry.execute`), conversation still works via a second, appended system prompt (`LOCKDOWN_SYSTEM_PROMPT`) that tells the LLM to acknowledge rather than attempt anything needing a tool. A few seconds after engaging, LLM/Whisper/Kokoro unload to standby (wake-word stays listening); disengaging calls the same `preload()` hotkey/wake-word already use.
  - State persists across restarts (`Core/data/lockdown_state.json`). HUD shows a lock indicator. Events logged to `Core/data/lockdown_log.jsonl`.
