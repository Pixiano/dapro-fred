## A. Efficiency / speed

- **Duplex path uses `DynamicCache`, not `StaticCache`/CUDA graphs.** `modeling_realtime_venus_omni.py:80` imports `DynamicCache` and the whole `streaming_prefill`/`streaming_generate` duplex loop (lines 1920-3550) reads/writes `self.llm_past_key_values` as a `DynamicCache`. `StaticCache` (line 82) and a CUDA-graph-recapture comment (line ~5274) exist only in the vendored generic HF `prepare_inputs_for_generation`/`_update_model_kwargs` boilerplate, which the duplex loop does not call. **Verified: no built-in static-cache/CUDA-graph path for duplex.** The community NVFP4 sidecar's 0.11-0.15 s talker step (cited in this try's README) used a *custom* static cache + CUDA graph wrapper outside the stock remote code — confirms it's buildable but not free; effort: medium-high, risk: medium (must stay correct under bnb NF4 dequant + varying prefill length; the vendored comment flags recapture triggers on non-contiguous `position_ids`).
- **`batch_vision_feed=True`** (`modeling_realtime_venus_omni.py:3107`) is real and already adopted (README: llm_feed 0.311→0.245 s, -21%). Already done, no further ask.
- **Sampling/turn-control knobs confirmed present and unused by us:** `listen_top_k`, `force_listen_count`, `max_new_speak_tokens_per_chunk` (default 20) at `modeling_realtime_venus_omni.py:2554-3347`, plus a documented compatible/native `length_penalty` override in `repo/demos/model/decoding.py`. `force_listen_count` forces N listen-decisions before the model is allowed to speak — could throttle over-eager speaking cheaply (no cost, since it only forces an existing branch). Effort: trivial; risk: low (behavior change only, easy to A/B). Untested locally — mark **unverified for effect on our latency**, only that the hook exists.
- **Quantization beyond bnb NF4:** README's own research (already captured, not re-derived here) found OpenBMB's official AWQ/GPTQ/GGUF builds of the base MiniCPM-o 4.5 LLM, and confirmed Venus adds no quant of its own — config is MiniCPM-o 4.5 + 4 tokens, same module names. AWQ/GPTQ would need re-mapping onto Venus's checkpoint (different weights, same architecture) — not a drop-in swap of quantized weights, only of *method*. GGUF/llama.cpp does not support the vision+audio+talker multimodal duplex path (llama.cpp multimodal support is chat-only, no known duplex/streaming server) — **unverified, worth a 15-minute check before ruling out**, but on priors this blocks GGUF for the realtime loop. Effort to try AWQ-style quant on Venus's own weights: high (need calibration data, may not preserve the bf16-skip-list correctness bnb already validated at cosine 0.996).
- No evidence in the repo or paper abstract of `torch.compile` being used anywhere in the served demo (`repo/demos/model/decoding.py`, `repo/demos/server/*` — grepped, zero hits for `torch.compile`/`compile(`). This is a real gap, not something upstream already solved for us; trying `torch.compile(mode="reduce-overhead")` on just the LLM decode step is the standalone SDPA-cache-compatible option **within** the stock path, unlike CUDA graphs which need the custom cache surgery already tried by the community. Effort: medium; risk: medium (NF4 layers + compile has known rough edges; recompilation storms if shapes vary — this loop already varies shape by design, i.e., variable frame counts per unit, so compile may thrash without a fixed max-shape wrapper).

## B. Running longer — memory module

- `models/Realtime-Venus-Omni/memory_adapter/model_adapter.py` is a thin loader; the real logic is a separate `omni_memory` package (imported from `memory_adapter.omni_memory.*` — not fully read here, budget). Confirmed structural facts:
  - `configure_memory(model, memory_minutes=None)` (`model_adapter.py:34-60`) builds a `RealtimeVenusOmniMemoryController`; `memory_minutes` maps straight to `duplex.archive.retention_seconds` in the memory config — this is the archive *window*, separate from the LLM's own sliding KV window.
  - **`duplex_factory_kwargs` hard-requires `sliding_window_mode="off"`** (`model_adapter.py:193-204`): `"Memory Duplex requires sliding_window_mode='off'"`, raises `ValueError` otherwise. **This directly conflicts with our current VRAM fix** (`sliding_window_mode="basic"`, 5000-token window) that stopped the VRAM-growth failure in live run 2. **Verified, load-bearing finding: the official long-video Memory feature and our context-trim fix are mutually exclusive as shipped** — enabling Memory means the KV cache grows unbounded again (the exact bug that caused the 17 s-lag run) unless the Memory package does its own trimming internally (plausible — it's designed for long video — but unverified from what was read).
  - So Memory does **not** obviously solve "our context-trimming problem" — it may replace it with archive-side retrieval, but wiring it in risks reintroducing the VRAM-growth bug we already fixed once, and needs its own VRAM/compute measurement before use. Effort: medium (mostly plumbing, `wrap_duplex()` already exists as an integration point at `model_adapter.py:206-216`); risk: medium-high (unverified compute/VRAM cost, and it fights the sliding-window fix).
  - Per README's paper notes (not re-verified against full text here): motion-gated frame archiving, 1 fps, max 128 frames, MaxSim token matching + MMR diversity — this is retrieval, not summarization, so archived frames still cost vision-encoder tokens when recalled. **Unverified**: exact VRAM/compute cost per recall, and whether the 128-frame cap is a hard limit or configurable.
- **"context" vs "basic" sliding-window mode:** `_window_config.sliding_window_mode == "context"` appears twice (`modeling_realtime_venus_omni.py:2850, 3409`) as a distinct branch from `"basic"` (line 3411) — a third trim strategy exists beyond what we're using. Not read in enough depth to characterize the difference; worth a 10-minute read before the next context-tuning pass. **Unverified what "context" mode actually preserves differently.**

## C. Quality for screen+voice use

- Paper abstract (WebFetch) confirms: two separately-trained 9B models (Omni = audio-visual, Audio = speech-only); dual-loop runtime (foreground continues while Harness executes async); full-duplex interruption response 75%, continuation rates 97/88/86% [these are Venus-Audio figures; Venus-Omni: interruption 0.60, same as base MiniCPM-o 4.5 — corrected 2026-09-30] under backchannel/other-directed/background speech — i.e. it's specifically trained not to stop for noise that isn't addressed to it, which matters for an always-listening desktop assistant.
- Project page (WebFetch) states the delegation benchmark numbers directly: **75.93% delegation accuracy for Omni, 68.89% for Audio** on an in-house benchmark — this is a harder number than the paper abstract gives and is consistent with README's already-captured "Omni under-delegates" caveat.

## D. Delegation / tools — harness wiring

Concrete and verified from `repo/harness/core/backend.py`, `delegate_parser.py`, `venus.py`:

- **Protocol**: model emits `<delegate>query</delegate>` inline in its token stream, never spoken (masked from TTS at both the token level in `modeling_realtime_venus_omni.py:3703-3730` and text level in `venus.py`'s `VenusOmniDelegateBridge`). Only one delegate span is allowed per model turn (`delegate_parser.py:9-14`); a second span or malformed span is rejected mid-stream, not fatal to the session.
- **Backend contract** (`backend.py:16-41`, a `Protocol`): `plan(request, candidates) -> RoutingDecision`, `execute(request, context) -> BackendResponse`, `oralize(request, source) -> BackendResponse`, `aclose()`. This is exactly the shape FRED's tool loop already has (route → run tool → render for speech) — the `oralize` step matches FRED's "read tool result aloud" behavior.
- **Result re-injection**: backend text comes back wrapped as `<backend>{sanitized}</backend>` (`venus.py:187-210`), with every Venus protocol token stripped from the backend's own output first, so a malicious/garbled tool result can't forge a second delegate span or fake a turn-end — a real prompt-injection guard already built in, complementary to (not a replacement for) FRED's own read/send-tool separation rule.
- **Design for wiring FRED's tools as the backend**: implement the three-method Protocol; `plan()` selects which of FRED's ~110 tools/agents to run given the delegate query text (this is where FRED's existing regex dispatcher + intent cues + embedding ranker slots in almost unchanged — it already produces a ranked tool list from free text); `execute()` calls the existing tool/agent and must still pass through FRED's confirmation gate — **this is the one hard requirement**: `execute()` in the Protocol is async and returns a `BackendResponse`, with no visible hook for "pause and ask the user" mid-execute. Confirmation-gated tools (send email, call, delete, etc.) cannot complete inside a single `execute()` call without either (a) blocking on a second audio/text turn from the user (awkward inside an async delegate call meant to run alongside ongoing conversation) or (b) `execute()` returning a "needs confirmation" `BackendResponse` that gets spoken as a question, and the *next* delegate call from a later Venus turn carries the user's yes/no back in — i.e., confirmation becomes a second delegate round-trip, not a synchronous gate. This needs actual design work, not just plumbing; effort: high; risk: high if skipped (this is exactly the mechanism that must never silently auto-confirm).
- Latency expectation: delegate spans are explicitly designed to run **asynchronously while the duplex loop keeps listening/speaking** (paper: "Foreground interaction continues while Harness executes tasks asynchronously") — so FRED's existing agent latency (web search, multi-tool chains) is likely fine as long as `execute()` doesn't block the GPU thread running Venus's own decode loop. Not verified whether the reference harness runs the backend in a separate process/thread by default — `repo/harness/core/runtime.py`/`scheduler.py` were not read in this pass; **unverified**.

## E. Fit verdict

**Better than current FRED at:** continuous screen+voice presence with a single model deciding when to speak (FRED today is push-to-talk/wake-word triggered, not always-on watching); built-in interruption/backchannel handling (FRED has none); a real async delegation protocol with injection-safe result re-injection (FRED's tool loop is turn-synchronous).

**Worse than / blockers vs current FRED today:**
1. **Confirmation gates don't map cleanly onto the delegate protocol** (D above) — FRED's hardest safety requirement has no obvious synchronous slot in Venus's async delegate/backend round-trip. This is the single biggest blocker to calling Venus "Mark II core" rather than a component.
2. **Delegation accuracy 68-76%** (project page) vs FRED's tool routing 83% / end-to-end 77.8% — Venus is not yet clearly better at deciding to delegate, and the paper's own caveat is under-delegation on Omni, over-delegation on Audio.
3. Realtime is not yet achieved with voice on at full quality (best measured 1.43 s/unit vs upstream's non-realtime-off Kokoro workaround already in place) — usable today only because Kokoro replaces Venus's own voice, which throws away Venus's trained speech-timing/backchannel behavior for output (input side interruption handling is unaffected).
4. Memory (long-run context) and our VRAM-safe sliding window are mutually exclusive as shipped (B above) — "running longer without losing context" is not solved yet, just worked around by trimming.
5. Small-screen-text quality is a measured, ongoing tuning problem (slices/scale), not a Venus defect but a real cost (672-scale run: only 65/70 realtime).
