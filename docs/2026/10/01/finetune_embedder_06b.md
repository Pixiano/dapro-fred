## 0. What FRED does today (read from local files)

- DOC (local): `memory_manager.py` loads one `Llama(embedding=True, n_ctx=4096, n_gpu_layers=GPU_LAYERS)` instance shared by memory, tool routing and vault routing. Vectors are L2-normalised in Python (`_normalize`) and stored in `IndexFlatIP`. Queries get a single fixed `Instruct: Given a search query, retrieve relevant passages ...\nQuery: {query}` prefix; documents get none.
- DOC (local): `tool_router.py` embeds ONE vector per tool = `"{name}. {description} {example phrasings}"` (documents), then nearest-neighbour on the query with `top_k=5, margin=0.06`. The query side uses `is_query=True`.
- DOC (local): `settings.py` ~1031-1052: 0.6B-f16 failed on "what are my priorities" (centered cosine -0.002 to -0.141 on the right file), so 4B Q4_K_M took over on 2026-08-03. Vault `chunks.json` must be deleted by hand after any swap; FAISS memory indexes self-heal on dimension mismatch.
- DOC (local): `research_components.md` s3 says "a small SetFit-style fine-tune ... likely beats any swap [I]" (an inference, not a measurement). `ASSEMBLED_FRED.md`: 0.6B Q8 ~0.7 GB vs 4B ~3.4 GB; the hybrid layout only fits 16 GB with the 0.6B (13.3 GB vs 16.0 GB).
- INF: the 0.6B failure was a single-file ranking miss on a vague, short query ("my priorities") against a file whose content likely does not use the word. That is a recall/vocabulary-gap failure that cheap fixes (title prefix, hybrid BM25, query rewrite) may already cover; settings.py line 59 already mentions heading-prefixing for that file ("Active Priorities - <heading>"), so some of that fix is already in.

## 1. How to fine-tune Qwen3-Embedding-0.6B

### 1.1 How Qwen trained it (DOC, arXiv 2506.05176 via HTML fetch [recheck numbers])
- Three stages: (1) weakly supervised contrastive pre-training on ~150M synthetic pairs generated by Qwen3-32B; (2) supervised fine-tuning on ~12M selected pairs (MS MARCO, NQ, HotpotQA etc. plus synthetic pairs filtered to cosine > 0.7); (3) model merging of SFT checkpoints with **slerp**.
- Loss: improved InfoNCE with temperature tau; denominator contains the positive, K hard negatives, in-batch queries and in-batch documents; **false-negative masking** (mask a candidate when its similarity exceeds the positive's score by 0.1, or it equals the positive doc).
- Embedding = last hidden state at the appended `[EOS]` (`<|endoftext|>`); input format `{Instruction} {Query}<|endoftext|>`. MRL supported (32-1024 dims).
- Ablation for the 0.6B (MMTEB mean task): full 64.33; no merge 62.56; no synthetic 61.21; synthetic only 58.49. Takeaway: merging checkpoints is worth ~1.8 points; INF: for a tiny domain fine-tune, averaging the base and fine-tuned weights (WiSE-FT style) is the cheap analogue and is the best forgetting guard.
- GAP: the paper text I got has no LoRA vs full detail, batch size, lr or tau value. Qwen's repo says training code is in "training docs" but no hyperparameters were visible [recheck github.com/QwenLM/Qwen3-Embedding].
- DOC: ms-swift (Qwen-endorsed trainer) default `INFONCE_TEMPERATURE=0.1`; supports full/LoRA/QLoRA/DoRA; one positive per anchor, hard negatives configurable. Pitfall noted there: the chat/template ending must match the model's own (`<|endoftext|>`). https://swift.readthedocs.io/en/v4.1/BestPractices/Embedding.html

### 1.2 Recommended method for FRED (INF unless tagged)
| Choice | Recommendation | Basis |
|---|---|---|
| Full FT vs LoRA | **LoRA r=16-32, alpha=2r, dropout 0.05, all linear projections (q,k,v,o,gate,up,down), lr 1e-4 to 2e-4.** Full FT at lr 1e-5 to 2e-5 is feasible on 16 GB for 0.6B but forgets more. | DOC: sbert PEFT example uses r=64/alpha=128, NDCG@10 0.4705 vs 0.4728 for full FT on NanoBEIR (adapter ~ full). DOC: a community Qwen3-Emb-4B adapter used r=16, alpha=32 with CachedMNRL (HF model page). INF: LoRA "learns less, forgets less" (Biderman et al. 2024, not fetched; GAP). |
| Loss | **MultipleNegativesRankingLoss with explicit hard negative column (anchor, positive, negative)**; use **CachedMNRL** only if you want batch >128 and VRAM is tight. | DOC: sbert recommends `BatchSamplers.NO_DUPLICATES` with in-batch-negative losses. |
| Temperature | sbert MNRL `scale=20` (tau 0.05) is the default; swift default tau=0.1 (`scale=10`). Start at scale 20 (sbert) or 10 (swift); try both. | DOC (sbert default scale=20: from my knowledge, recheck); DOC swift 0.1. |
| Batch size | Larger is better for in-batch negatives: 64-128 per step (CachedMNRL lets 256+ with mini-batch 16-32). Philschmid: global batch 512, 4 epochs, lr 2e-5, cosine, warmup 10% for a 109M model. | DOC https://www.philschmid.de/fine-tune-embedding-model-for-rag |
| Epochs | 1-3 for LoRA on >5k triples; up to 4 on small sets with early stopping on the held-out eval. | INF |
| Max seq length | Queries 64 tokens; vault chunks 256-512; memory turns 256. Set `max_seq_length=512` and train separate length buckets only if needed. | INF |
| Hard negatives | Mine with `sentence_transformers.util.mine_hard_negatives` using the base model, skip the top 1-3 (likely false negatives), take ranks ~5-30, apply a margin / relative margin vs the positive score. | DOC function exists (util.hard_negatives); parameter detail GAP [recheck docs]. Qwen's false-negative masking (0.1 margin) is the same idea. |
| MRL | **Skip it for FRED.** MRL only matters if you want <1024 dims; truncating changes the FAISS dim and costs quality. If you train with `MatryoshkaLoss` anyway, add dims 1024/512/256 but ship 1024. | DOC: Qwen supports MRL 32-1024; Philschmid shows a +22% gain at 64 dims, +7% at 768 (small, FT-specific). |
| Instruction | **Train with the exact production prefix** (`Instruct: ...\nQuery: ...`) on the query side only, documents bare. For routing use a separate, shorter task instruction ("Given a spoken request, retrieve the tool that should handle it") and keep it fixed for training and inference. FRED currently shares one instruction across three jobs; fine-tuning is the moment to split. | DOC: model card says instructions give +1-5%; English instructions recommended. |
| Pooling | Last token (EOS). Do not change. | DOC |

### 1.3 Pitfalls
- DOC: `padding_side="left"` for the HF tokenizer (Qwen model card / repo). With right padding last-token pooling picks a pad token. sentence-transformers' Qwen3 config handles this when loaded via `SentenceTransformer("Qwen/Qwen3-Embedding-0.6B")`; check `model.tokenizer.padding_side`.
- DOC: EOS `<|endoftext|>` must be appended; HF tokenizer does it for the embedding repo; if you build your own dataset with a custom tokenizer call, verify the last token id is 151643. INF: the most likely silent bug is training with EOS and serving without it (or vice-versa) in llama.cpp (see section 5).
- DOC: requires `transformers>=4.51.0`.
- INF: normalise (L2) at inference (FRED already does) and make sure the training similarity is cosine (sbert default).
- INF: because FRED applies a "centering" step in the vault router, re-fit the center after fine-tuning; the old mean vector is meaningless in the new space.
- INF: de-duplicate (anchor, positive) pairs; duplicate chunks create fake in-batch negatives (false negatives). Use NO_DUPLICATES sampler.

### Minimal recipe outline (do NOT run without approval; no GPU use in this task)
```python
# train_embed.py  (outline)
from sentence_transformers import SentenceTransformer, SentenceTransformerTrainer, SentenceTransformerTrainingArguments
from sentence_transformers.losses import MultipleNegativesRankingLoss      # or CachedMultipleNegativesRankingLoss
from sentence_transformers.training_args import BatchSamplers
from sentence_transformers.evaluation import InformationRetrievalEvaluator
from peft import LoraConfig, TaskType
from datasets import Dataset

m = SentenceTransformer("Qwen/Qwen3-Embedding-0.6B", model_kwargs={"torch_dtype": "bfloat16", "attn_implementation": "sdpa"},
                        tokenizer_kwargs={"padding_side": "left"})
m.max_seq_length = 512
m.add_adapter(LoraConfig(task_type=TaskType.FEATURE_EXTRACTION, r=32, lora_alpha=64, lora_dropout=0.05,
              target_modules=["q_proj","k_proj","v_proj","o_proj","gate_proj","up_proj","down_proj"]))
# columns: anchor (WITH the production Instruct prefix), positive, negative  -> triplet MNRL
loss = MultipleNegativesRankingLoss(m, scale=20)
args = SentenceTransformerTrainingArguments(output_dir="out", num_train_epochs=2, per_device_train_batch_size=64,
        learning_rate=1e-4, warmup_ratio=0.1, lr_scheduler_type="cosine", bf16=True,
        batch_sampler=BatchSamplers.NO_DUPLICATES, eval_strategy="steps", eval_steps=100, save_steps=100,
        load_best_model_at_end=True, dataloader_num_workers=0)
SentenceTransformerTrainer(m, args, train_dataset=train, loss=loss, evaluator=ir_eval).train()
# then merge LoRA into base weights and save HF safetensors (see s5)
```
Note: with ST and a causal LM, training in bf16 on RTX-class 16 GB is fine; fp16 can overflow on some Qwen layers [INF].

### 3.1 How many triples
- DOC: Philschmid, bge-base (109M), 6.3k synthetic (question, context) pairs, MNRL+Matryoshka, 4 epochs: NDCG@10 0.7684 -> 0.8254 at 768d (+7.4%), trained in ~3.5 min on one g5.2xlarge. Note the base was already strong. [recheck]
- DOC: Databricks, synthetic sets of ~6k / ~8.7k / ~14k pairs, in-batch negatives only: gte-large Recall@10 FinanceBench 0.293 -> 0.552; ManufactQA 0.821 -> 0.873; DocsQA 0.849 -> 0.884. | Regime | Triples | What to expect (INF) |
|---|---|---|
| Minimum useful (routing) | 40 tools x 30-50 utterances = 1.2k-2k | Clear gain on tool routing; high overfitting risk without held-out phrasing |

### 3.2 Synthesising without leaking personal content into git
Rules from memory: never quote vault content in messages/comments/tests; vault lives outside the repo; sensitive data goes to cloud APIs only under Vatsal's explicit flag (it is currently off for local-only meaning personal/ may go to cloud APIs by his call; do not rely on that for training data without asking again).
- INF: generate the vault data **locally at run time**, write outputs only to a path outside the repo or in an ignored dir (e.g. `Core/data/` which is untracked; confirm `.gitignore`), and commit only the generator script plus aggregate metrics (no queries, no chunk text). Prefer a local LLM (FRED's own Qwen/LFM) for vault-derived queries so nothing leaves the machine; this also respects "no cloud for personal" if that flag is later re-armed.
- Tool routing data (no personal content, safe to commit): from each tool's description + example list, have an LLM write 30-60 spoken utterances per tool in English, Hinglish (romanised Hindi mixed with English, plus a few Devanagari), with disfluencies, ASR-style errors, short imperative forms, and indirect requests. Add **near-miss negatives**: utterances for sibling tools (e.g. volume up vs brightness up; set timer vs set alarm) as the hard negative. Generation can use any strong model because it contains no personal data.
- Memory recall data: for each stored turn (or turn pair), generate 2-3 later-style recall questions ("what did I say about X", paraphrased, partial, time-referenced). Positive = the turn; hard negatives = other turns on the same topic from different dates (mine via base model).
- Vault data: per chunk (heading-prefixed, exactly as embedded in production), generate 2-4 questions of varying specificity, **including vague ones** ("what are my priorities"), which is the known failure mode. Hard negatives: other chunks in the same file and sibling files.
- Hard-negative classes to hand-build (INF): negation ("I do NOT want X" vs "I want X"), temporal ("last week" vs "next week"; "before/after"), numeric (different amounts/dates/times, alarm 6:30 vs 7:30), entity swap (names), and polarity of intent (turn on vs off). Embedders are known to be weak on these; but contrastive training on them may not fully fix it (GAP: no fetched evidence). Verify with the held-out eval.
- Quality filter (DOC, from Qwen's pipeline): keep a synthetic pair only if the base model scores it above a threshold (Qwen used cosine > 0.7) or the round-trip check works (the query retrieves its own chunk in top-k); then mask false negatives (Qwen: 0.1 margin).
- Hinglish: GAP - I found no published Hinglish retrieval benchmark for Qwen3-Embedding. Build your own eval; do not assume the multilingual MTEB number covers romanised Hindi. granite-r2 lists Hindi among 52 optimised languages (DOC) but romanised/code-mixed is not stated.

### 3.3 Leakage and held-out eval
- Split **by source**, not by pair: hold out whole vault files / whole conversation days / whole tools' phrasing templates so no chunk, near-duplicate chunk or paraphrase of the same source appears in train and eval. Never generate eval queries with the same prompt/LLM call that produced the train queries for the same chunk.
- Keep a hand-written eval (Vatsal-authored or real logged utterances from session logs) of ~100-200 routing utterances and ~50-100 vault/memory queries; frozen, never used for training or hyperparameter picking beyond early stopping (use a separate dev split for that).
- Also hold out a **general-retrieval canary** (e.g. a NanoBEIR or small MTEB subset) to measure forgetting (s4).
- Metrics: routing top-1 and top-3 (FRED keeps near ties within margin), vault MRR@5/Recall@5, memory Recall@5, plus margin between best and second-best tool score. Compare 0.6B base, 0.6B + cheap fixes, 4B, and the fine-tune on the same sets.

## 4. Risks and expected gains

- Catastrophic forgetting: DOC (search summary) LoRA forgets less than full FT but not zero (arXiv 2501.15377 / 2512.17720 [recheck]). GAP: no embedding-specific forgetting numbers retrieved. Mitigations (INF): LoRA, low lr, 1-2 epochs, include a replay slice of generic query-passage pairs (e.g. 20-30% from a public set like MS MARCO / NQ), and weight-space interpolation with the base (mirrors Qwen's merge step; their ablation shows merging +1.8 points).
- Overfitting to a small vault: INF high risk if you train on chunks you then evaluate on. The model learns vault-specific vocabulary; fine for FRED (the vault is the domain) as long as new notes are phrased similarly. When the vault changes, the model needs no retrain, but quality on genuinely new topics reverts toward base.
- Short utterances vs long chunks: INF routing queries are 3-12 tokens with a single instruction; training mixing 8-token utterances and 400-token chunks in one batch is fine for MNRL but use separate losses/datasets per task (sbert supports multi-dataset dict training) so the in-batch negatives are task-pure. Tool descriptions are documents; keep their format identical to `tool_router.build()` (name. description + examples).
- Gains: DOC published domain-adaptation gains of +4 to +25 points (Recall@10) for 100M-7B embedders on 6k-14k synthetic pairs; bigger when the base is weak. For FRED the 0.6B base vs 4B gap on MTEB is ~5 points (64.33 vs 69.45 MMTEB, DOC local). INF: a task fine-tune plausibly closes the 4B gap on vault and routing; it will NOT make the 0.6B better than 4B on open-domain recall.
- **Is a SetFit / classifier head better for tool routing than embedding fine-tuning? (evaluate the research note's claim)**
  - DOC: SetFit gets competitive few-shot classification from ~8 examples/class by contrastive fine-tune + a logistic head (https://nips.cc/virtual/2022/59466 [recheck]). A summarised result also warns SetFit scales poorly with many classes (GitHub issue "setfit for a large number of classes", not read).
  - INF: with ~40 tools and hundreds of utterances per tool, a plain linear/MLP head (or kNN) on frozen or fine-tuned embeddings is strong, tiny (KBs), costs ~0 VRAM, gives calibrated probabilities and a natural "none of these" threshold. Its weaknesses: closed-set (a new tool needs retraining; FRED adds tools often), no use of tool descriptions, and no help for memory/vault retrieval. The embedding-based router handles new tools zero-shot from a description.
  - Verdict: the claim "a small fine-tune likely beats a swap" is plausible but UNTESTED (research note marks it [I]); partially true for routing. Best design (INF): keep embedding retrieval for candidates (top-5 within margin, as today), and add a light head or a rerank-by-kNN over logged real utterances as a tie-breaker. Evaluate classifier head on frozen 0.6B first: zero training risk, no GGUF change, no cache invalidation. If frozen-0.6B + head matches 4B on the routing suites, routing no longer needs fine-tuning at all, and fine-tuning is only for vault/memory.

## 5. Deployment back to FRED

1. Merge LoRA: `peft` `merge_and_unload()` on the base in bf16/fp32, save HF safetensors (config, tokenizer, `modules.json`, pooling/normalize configs if saving via sbert). Prefer merging in fp32 then saving bf16/fp16.
2. Convert: `python convert_hf_to_gguf.py <merged_dir> --outtype f16 --outfile q06-ft-f16.gguf` using a llama.cpp checkout that supports `Qwen3Model` embedding (the official Qwen3-Embedding-0.6B-GGUF was built with "latest llama.cpp", DOC https://huggingface.co/Qwen/Qwen3-Embedding-0.6B-GGUF). Then `llama-quantize q06-ft-f16.gguf q06-ft-Q8_0.gguf Q8_0`. Official sizes: Q8_0 639 MB, F16 1.2 GB (DOC), matching the ~0.7 GB budget.
3. Pooling and EOS (the part most likely to bite):
   - DOC: official usage is `llama-embedding ... --pooling last` and `llama-server --embedding --pooling last -ub 8192`. The converted GGUF should embed `pooling_type = LAST` in metadata so llama-cpp-python needs no flag; **verify** by reading GGUF metadata after conversion (`gguf-dump`) [INF].
   - DOC (search snippet, not verified): llama.cpp asserts if `add_eos` is set in some embedding configs (`GGML_ASSERT(llama_add_eos_token(model) != 1)`); and a separate open-then-closed issue (#18910) shows a tensor-read assertion with `--pooling last` on Qwen3-VL-Embedding 2B Q4_K_M on Windows CPU (context 256) - not the same model, closed "not planned", but a warning to test on Windows [recheck].
   - INF: Qwen's HF tokenizer appends `<|endoftext|>`; llama.cpp's Qwen3 conversion may or may not append EOS depending on `tokenizer.ggml.add_eos_token`. The cosine test below is the only reliable way to know; if the GGUF vectors do not match, append `<|endoftext|>` to every string FRED sends (both the shipped 4B and 0.6B GGUF behaviours must be checked with the same test, since FRED currently works with the 4B GGUF).
   - Normalisation: FRED normalises itself in `_normalize`; llama.cpp may also return normalised vectors (`--embd-normalize`); double-normalising is harmless.
4. Verify with llama-cpp-python 0.3.31 (GAP: I did not confirm this release or its bundled llama.cpp date; check it supports the converted arch): encode ~200 strings (queries with the Instruct prefix, plus chunks) in (a) HF/sbert fp32 and (b) the Q8_0 GGUF through `Llama(embedding=True)`; assert mean cosine >= 0.99 per text (Q8_0 should be ~0.999; f16 ~0.9999); also assert ranking agreement on the held-out eval (top-1/MRR within 1 point of HF). Run the same on the unmodified base 0.6B GGUF first to calibrate what "normal" mismatch looks like.
5. Cache cost: new model => (a) FAISS memory index self-heals only on dimension change; **the dimension is unchanged between 0.6B (1024) and 4B (2560)? No: 4B is 2560-dim, 0.6B is 1024-dim [INF from model configs, recheck], so switching 4B -> 0.6B triggers self-heal re-embed of all memory turns**; but a fine-tuned 0.6B replacing a base 0.6B (same 1024 dims) would NOT trigger it and would silently mix old and new vectors in FAISS [INF from the code comments: dimension-mismatch check only] - force a rebuild (`_rebuild_index`-style path exists, line ~238). (b) Delete the vault `chunks.json` cache by hand (settings.py note). (c) tool_router vectors rebuild at startup (40 embeds). (d) re-fit the vault centering vector and re-check the thresholds (`floor`, `margin=0.06`, vault score floor -1.0) since fine-tuning shifts the score distribution.
6. MRL implication: if you ever ship <1024 dims, FAISS dim changes and cosine thresholds shift; avoid unless storage matters (it does not at this scale).

## 7. Hardware and time (all INF; GAP: no measured numbers for 0.6B on this GPU)

- 0.6B LoRA in bf16, seq 128-512, batch 64: weights 1.2 GB + activations. With gradient checkpointing, expect ~4-8 GB; full FT with AdamW states ~10-12 GB (1.2 weights + 1.2 grads + 4.8 fp32 Adam states + activations). CachedMNRL for batches >128 keeps memory flat. Fits on one 16 GB GPU only if FRED's other models are NOT resident (the brain, Kokoro, etc. consume ~7.7 GB today); policy in memory is "never kill processes, flag if it won't fit", so the training run must be scheduled while FRED is stopped by Vatsal, or on a smaller batch + cached loss with FRED up if headroom exists (probably not).
- Time estimates (RTX-class 16 GB, 0.6B, LoRA, seq ~128 avg, batch 64, 2 epochs; throughput assumed 150-400 triples/s because each triple = 3 forward + backward passes): 2k triples ~1-3 min; 10k ~5-15 min; 50k ~25-75 min. Add mining time (embedding the corpus with the base model and FAISS search: minutes). Philschmid measured 3.5 min for 6.3k pairs x 4 epochs on a 109M model (DOC); a 0.6B is ~5-6x heavier [INF], so ~10-20 min for that same job.
- Generation of data with an LLM dominates wall-clock (hours for 10k+ items on a local model), not the training itself.
- Eval after training: encode a few thousand texts, seconds.

## (a) Step-by-step plan with decision gates

0. **Do not start with training.** Freeze the wake-word model per memory rule (unrelated, but the same "no unrequested redeploy" attitude applies: nothing replaces the production embedder without Vatsal's go).
1. **Build the eval first** (no GPU needed beyond what FRED already uses): ~150 routing utterances (EN + Hinglish, include logged real ones from the session jsonl files, not committed), ~50 vault queries incl. vague ones, ~50 memory queries; record top-1/top-3/MRR for current 4B. *Gate 1*: you have a number for the 4B and the base 0.6B-Q8 on all three. This also tells you how big the real gap is (the 2026-08-03 comparison was based on one file and an f16 0.6B).
2. **Cheap fixes on the base 0.6B Q8** (title prefixes, per-job instructions, centering for routing/memory, BM25+RRF, more example phrasings per tool). *Gate 2*: if 0.6B + fixes is within ~2 points of the 4B on routing and ~3-5 points on vault/memory, STOP: no fine-tune needed. Take the VRAM saving.
3. **Frozen-0.6B + kNN/linear head for routing** (needs no GGUF change). *Gate 3*: if it matches the 4B router, routing is solved; remaining gap is vault/memory.
4. **Optionally add Qwen3-Reranker-0.6B** (ggml-org GGUF) for vault/memory top-10 only. Test latency in-process. *Gate 4*: accept if it recovers >= half of the remaining gap at < ~100 ms and ~0.7 GB.
5. **Only then fine-tune** (LoRA, section 2 recipe) if a gap remains > 3 points on vault/memory after steps 2-4. Generate data locally, split by source, train 1-2 epochs, interpolate with base (alpha 0.5-0.8), evaluate against base on the frozen eval and a general-retrieval canary. *Gate 5*: ship only if held-out gain >= +3 points on target tasks and < 1-2 points loss on canary.
6. **Deploy**: merge, convert, Q8_0, cosine >= 0.99 vs HF, retrieval parity, then delete `chunks.json`, force FAISS rebuild, re-fit centering and thresholds, rerun routing suites. Keep the 4B GGUF on disk for one-line rollback via `EMBEDDING_MODEL_PATH`.

**When NOT to fine-tune**: the gap closes with cheap fixes; the eval set is under ~100 queries (you cannot tell signal from noise); the vault changes shape often (tune on stale topics); you cannot hold out by source; or VRAM headroom for training would require stopping FRED and the benefit is under 3 points.

## (c) Recommendation and main uncertainty

Recommendation: do **A, then F, then C only if needed, and fine-tune (B) last**. The research note's "fine-tune beats a swap" is an unmeasured inference, and the original 0.6B failure was a single vague query against one file, likely a vocabulary gap that title prefixing, hybrid BM25+RRF and a rewrite step can cover without touching weights. Fine-tuning is the right tool only if gates 2-4 leave a measured gap above ~3 points. If it is needed: LoRA r=32 on sentence-transformers v5, MNRL with mined hard negatives, locally generated data split by source, weight-interpolated with the base, verified by cosine >= 0.99 against the GGUF.

Main uncertainty: nobody has measured (on FRED's own data) how large the real 0.6B-vs-4B gap is once the cheap fixes are applied. Secondary GAPs: the llama-cpp-python 0.3.31 behaviour for EOS/last-pooling on a freshly converted Qwen3 GGUF, rerank support in that wrapper, Windows Unsloth support, and any Hinglish retrieval evidence for Qwen3-Embedding.
