# LLM and Model Tiers

Ground truth for everything in this file: `Core/config/settings.py` (the "LLM SETTINGS" and "IDLE MODEL UNLOADING" sections), `Core/llm/llm_client.py`, `Core/llm/vision_server.py`. Re-read those directly before relying on any specific number here — this subsystem has been revised multiple times in single days and the comments record the exact history.

## Two independent systems, tried in order: cloud cascade, then local tiers

`LLMClient` (`Core/llm/llm_client.py`) is **not** "local with a cloud option" — it is a cloud cascade tried first on *every* call, which falls through, completely untouched, to the original all-local tier system only once every cloud provider has failed. The local system was not modified to accommodate the cloud cascade; it runs exactly as it did before the cascade existed, as the tertiary path.

1. **`CLOUD_PROVIDERS`** (settings.py) — currently a single entry: Cerebras, model `gpt-oss-120b`, OpenAI-compatible `/v1/chat/completions`. (Groq was removed 2026-08-05 — see below.) Each provider dict: `name`, `base_url`, `api_key`, `model`. `LLMClient._cloud_providers()` filters to providers with a truthy `api_key`, so setting a key to `None` removes it from the cascade in one place.
2. **Local tier system** — `MODEL_TIERS` dict, `llama-cpp-python`, GGUF files loaded straight from disk via `Llama(...)`. Reached only when `_cloud_generate`/`_cloud_stream` raises after exhausting every provider.

Both cloud providers' data-processing terms were checked before wiring this in: neither trains on API inputs/outputs. Groq — no retention by default (30-day abuse/troubleshooting log only, itself opt-outable). Cerebras — no retention at all, inputs/outputs processed for the response and immediately discarded. The real exposure is "this leaves the machine and is processed on a third party's servers", not "they train on your vault" — judged acceptable for FRED's own conversation content, explicitly *not* a reason to route raw financial/ID documents through it.

### Groq's removal (a concrete gotcha worth reproducing correctly)

Groq was tried first in the cascade, then removed entirely 2026-08-05, not just deprioritized — a live probe against the API showed `Limit 8000, Requested 15076` tokens/minute: one FRED request is ~15k tokens (system prompt alone ~7k, the unfiltered tool menu another ~5k) — nearly double Groq's *entire* free-tier per-minute allowance, so every call 413'd regardless of how quiet the preceding minute had been. 100% failure rate over two days (24/24 on the last day) while Cerebras silently carried every turn. Leaving Groq first in the cascade cost a guaranteed-dead round-trip before every real request. **Lesson for a rebuild**: don't assume a provider's advertised free tier covers a system-prompt-heavy tool-calling agent; measure the actual request size against the real per-minute token limit before wiring a provider in as primary.

### Rate-limit handling

`_cloud_request()` treats an HTTP 429 as a per-minute throttle, not an outage — Cerebras' free tier allows 5 req/min and a single tool-calling turn can fire four requests in two seconds. On a 429, it waits out `retry-after` (capped at 15s, default 12s if the header is absent) once, then gives up and lets the caller fall through to local. Before this fix, a single throttled request ended the whole turn with a "cognitive malfunction" reply (confirmed in a session log).

### `TIER_ROUTING_ENABLED = False`

`_pick_tier()` contains a real word-count/keyword heuristic (extreme_signals / deep_signals word lists + minimum word counts) that would route "why/explain/debug/..." messages to Deep and "comprehensive/thorough/..." messages to Extreme — but it's gated behind this flag, currently off. When off, `_pick_tier` always returns `DEFAULT_TIER`. This is deliberately not deleted: the plan is a future "offer the bigger model, ask before switching" UX rather than silent routing, so a tier change is never a surprise mid-conversation.

### Context windows (`CONTEXT_WINDOW_BY_TIER`)

Standard: 24576 (raised from the global default 16384 on 2026-08-02 — Qwen3-8B at the time trained at 32768 so 16384 left capacity on the table, and the vault-chunk budget had just grown). Measured VRAM/latency tradeoff at n_ctx 16384/24576/32768 on the venv's CUDA build (4026-token prompt): generation speed is flat across all three (~4.2-4.4s) — this is purely a VRAM decision. 24576 keeps ~2GB of worst-case headroom (accounting for Whisper's ~1.3GB when resident and a 1.2-3.1GB non-FRED baseline) on a 16310 MiB card with a documented crash history; 32768 is reachable but only "knowingly", not by default. Backup/Deep/Extreme: 16384 (not raised — bigger models, so the same increase costs more VRAM, and only one tier is ever resident anyway). Vision: 4096, deliberately small — a screen description is a sentence or two, and this is the one tier that can be resident in a *separate process* from the conversation model, so it doesn't get the "only one resident tier" VRAM guarantee the others do.

### GPU offload

`GPU_LAYERS = -1` — offload all layers to GPU. Confirmed the venv's `llama-cpp-python` (0.3.31) is a genuine CUDA build (`llama_supports_gpu_offload()` is True). Repeats the "three Pythons on this machine" gotcha from `01_environment_and_setup.md` — always benchmark with `Core/venv/Scripts/python.exe`.

### Only one tier resident at a time

`_get_model()` evicts every currently-loaded tier before loading a new one (`if self._loaded: ... self.unload()`). Measured 2026-08-02: Standard (Qwen3-8B Q4_K_M) at n_ctx 24576 alone peaks ~9.9GB of a 16310 MiB card; a second multi-GB tier resident simultaneously cannot fit, and this machine has a documented history of hard access-violation crashes (0xc0000005) from exactly that. This was latent (nothing used to request a second tier) until `tools/smart_search.py::find_file_smart` started being able to pull in "Deep" alongside an already-resident tier on a single turn — the eviction guard is what prevents that from crashing. Cost: a reload when alternating tiers, judged rare enough to accept.

### Thinking / reasoning toggle

`THINKING_LENGTH_THRESHOLD = 175` (chars of the latest user message) — **temporary as of 2026-08-20**: since every text tier currently resolves to the same Qwen3.5-4B checkpoint, there's no more per-tier reasoning-on/off distinction to make, so thinking now toggles dynamically per call instead: `enable_thinking = len(last_user_text) > THINKING_LENGTH_THRESHOLD`, computed fresh in `llm_client._native_call()` (and mirrored in `vision_server.describe_image()` using the same threshold against a `thinking_signal_text` argument). Raised from 75 → 175 same day it was introduced: `generate_stream()` withholds the entire `<think>...</think>` block from the caller by design (documented as "the fix for dead air"), so a thinking-mode turn is *total silence* for the whole reasoning phase (60-110+s measured), then the full answer arrives at once. At 75 chars this engaged on nearly every normal message; 175 keeps ordinary conversation on the fast, actually-streamed path and reserves reasoning for messages that look like they genuinely need it. **A rebuild should not treat 175 as a fixed constant — it is a length-based reasoning gate that must be retuned per model/UX, and its own comment says so.**

`enable_thinking` is threaded through by calling the tier's own chat-template handler *directly* rather than through `create_chat_completion()`, because that method has a fixed keyword signature with no `**kwargs` passthrough (confirmed by reading its source) — there is no way to set `enable_thinking` through it. `_native_call()` bypasses it and calls the handler (`Jinja2ChatFormatter` built from the model's own embedded `chat_template`, or the model's existing `chat_handler` for Vision) directly, which *does* accept arbitrary kwargs and forwards them into the jinja render. This is the load-bearing trick that makes the length-based reasoning toggle possible at all — earlier attempts injected `/no_think`-style text into the prompt (`TIER_PROMPT_MARKERS`) and were confirmed live *not* to work, because the guard in the actual chat template checks the real `enable_thinking` jinja variable, not any string in the prompt text.

### Streaming, cancellation, and reasoning-stripping (chat path only)

`generate_stream()` exists specifically so speech can start on the first finished sentence instead of after the whole reply — "the fix for dead air." It only runs on turns that need no tools (a tool result can't be narrated before the tool has run; the intent router already separates chat from tool turns). It withholds any `<think>...</think>` or Gemma-style `<|channel>thought...<channel|>` reasoning block from the stream entirely — a state machine (`unknown` → `thinking` → `done`) buffers until it can tell which case it's in, and only emits real content once past a reasoning block (or once it's confident no reasoning block is coming). It also holds back partial `{...}` JSON (a tool call the chat handler failed to lift out of plain-text content) until the matching closing brace arrives, using brace-depth counting rather than "first `}`" — because a real tool call's arguments object is itself nested, and stopping at the inner brace would leak the outer wrapper's tail. This exists because of a confirmed live incident: FRED spoke `{"name": "list_tasks", "arguments": }` aloud after a naive first-`}` strip cut only the inner empty object.

**Cancellation**: `generate_stream()` itself takes no cancel flag and needs none. `create_chat_completion(stream=True)` is a Python generator wrapping llama.cpp's token loop — the next token is only decoded when something calls `next()` on it. The *caller* (`pill_app.py`) holds a `_cancel` Event (also used to stop the TTS queue); its producer thread's `for piece in ...` loop checks `_cancel.is_set()` each iteration and returns immediately, abandoning the generator without exhausting it. Measured: GPU utilization drops from 74% to 1% within 0.2-0.4s of that return executing — Python's refcount-based cleanup closes the whole generator chain almost immediately. This does **not** extend to `generate_with_tools()` — that path is a single blocking (non-streaming) call, and llama-cpp-python's public API doesn't expose the lower-level `stopping_criteria` hook that would allow the same trick; a tool-calling turn genuinely cannot be interrupted mid-generation today. This was a deliberate non-fix: reimplementing chat-template application to call `create_completion()` directly risks diverging from library-maintained, tested tool-calling formatting, for a speed-of-interrupt win on turns that are already the minority.

### Reasoning-block stripping (non-streaming path) — real failure modes fixed here

`_strip_thinking()` handles two reasoning syntaxes: `<think>...</think>` (DeepSeek-R1/Nemotron-style) and Gemma 4's paired `<|channel>thought...<channel|>` markers. Two confirmed-live failure modes it specifically guards against:

1. **Unterminated reasoning block → empty string → total silence.** If a model opens a reasoning block and runs out of `max_tokens` before closing it, `_strip_thinking` returns `""` rather than trying to parse a dangling block. Both `generate()` and `_strip_thinking_for_tools()` explicitly check for this and substitute an honest spoken fallback ("I ran out of room thinking that one through, sir...") — confirmed live in a session log where three consecutive turns logged `"text": ""` with `spoken: true` and FRED said literally nothing.
2. **Unparsed tool-call JSON getting spoken verbatim.** `_strip_tool_call_debris()` strips `<tool_call>` wrappers and bare `{...}` objects from content the chat handler failed to recognize as a real tool call. Confirmed live: FRED once spoke `{"path":"daily/2026-08"}We need to list directory.{"path":"daily"}...` aloud verbatim because Qwen3's template emits tool calls inline and llama.cpp only lifts the *first* one out, leaving any others as plain text. This stripping is applied with `debris=True` on the plain-chat path but `debris=False` on the tool-calling path (`_strip_thinking_for_tools`) — the orchestrator needs to see and parse a tool call the model wrote as plain text, and stripping first would erase evidence the orchestrator still needs (confirmed live: a today's-tasks question had its `list_tasks` call erased this way, and the model then falsely answered "no tasks recorded" for a day with six of them).

### `_apply_thinking()` — message-list adaptation for native-template tiers

Two adjustments applied to a **copy** of the message list (never mutates the caller's list — the orchestrator reuses message history across turns, so mutating would stack markers): (1) inject a tier's `TIER_PROMPT_MARKERS` entry if present (best-effort text override for models whose template doesn't expose a real controllable kwarg — currently only `Extreme`/gpt-oss's `"Reasoning: high"`, not confirmed live to actually override the template's own default "Reasoning: medium" line); (2) for any tier keeping its own native chat template (`CHAT_FORMAT_BY_TIER[tier] is None`), convert prior tool-call arguments from JSON string back to a dict — the OpenAI wire convention uses a string, but some models' own templates (Gemma 4 did) call `raise_exception()` on a string argument when replaying tool-call history for a follow-up turn, aborting generation entirely.

### `CHAT_FORMAT_BY_TIER`

Global default when unset: `chatml-function-calling` — most local GGUFs' own embedded chat templates have no provision for tool definitions at all, and without an override llama.cpp silently never shows the model its tools. Standard/Backup/Deep are set to `None` (use the model's own embedded template) because Qwen3/Qwen3.5's own templates handle both tool_calls and reasoning correctly on their own. Extreme (gpt-oss-20b) deliberately has no entry — its Harmony-format template has its own tool-calling/channel conventions that `chatml-function-calling` would silently override; reasoned to likely be worse but **not tested either way**.

## Vision — a structurally different path from text tiers

Vision does **not** run through `llm_client._get_model("Vision")` in-process. It runs through `Core/llm/vision_server.py`, which spawns `llama-server.exe` (llama.cpp's own prebuilt binary, release b10509, from `LLAMACPP_BIN_DIR`) as a subprocess and talks to its OpenAI-compatible HTTP API on `VISION_SERVER_PORT = 8090`.

**Why**: confirmed 2026-08-20 through extensive live testing (documented in detail in `settings.py`'s `MODEL_TIERS["Vision"]` comment) — `llama-cpp-python` 0.3.31's in-process multimodal handlers (`Gemma4ChatHandler`, `MTMDChatHandler`, `Qwen25VLChatHandler`) give **wrong output** on this model family's vision path: tested with Bonsai-27B and with Qwen3.5-4B through two different handlers, all four combinations produced the same "find_slot: non-consecutive token position" warning and hallucinated/wrong descriptions (e.g. describing a real, non-blank screenshot as "a large exclamation mark" or "a blank computer screen"). Raw llama.cpp binaries (`llama-mtmd-cli.exe`, `llama-server.exe`) on the **identical** model+mmproj files got it exactly right, with the same cosmetic warning printed either way — confirming the bug lives in llama-cpp-python's Python binding layer, not in llama.cpp itself, and not in the model/mmproj files. **Lesson for a rebuild**: if local multimodal inference through `llama-cpp-python` produces plausible-looking but wrong image descriptions with this warning present, don't keep debugging the binding — go straight to the subprocess-over-HTTP approach against the vendor's own binaries.

### `vision_server.py` lifecycle

- **Lazy-started** on the first `describe_image()` call, left resident after that (same "load once, keep warm" pattern as `llm_client._get_model()`).
- **Idempotent `ensure_running()`**: checks `/health` over HTTP first; safe to call from either FRED's main process or the screen watcher's separate child process, since readiness is checked over the network, not local in-process state.
- **Cleanup relies on the Windows Job Object** (`utils/process_group.py`), not `atexit`. Deliberately **not** atexit-registered: whichever process happens to spawn the server first (e.g. a one-off screen-watcher capture) would kill it the moment *that* process exits, even though the server should outlive it — confirmed live 2026-08-20, a short-lived test script's own exit was silently killing the server between calls. The Job Object, assigned once at FRED's real startup and inherited transitively by every process FRED creates including grandchildren, is what correctly ties the server's life to FRED's main process regardless of which process actually spawned it. `shutdown()` exists for an explicit, intentional stop (FRED's own real shutdown sequence) but is never auto-registered.

### Cloud vision first

`describe_image()` in `llm_client.py` tries `CLOUD_VISION_PROVIDER` (Cerebras, model `gemma-4-31b`, **separate** from the text cascade — different, larger, vision-capable model) before falling back to the local `vision_server.py` subprocess. Added specifically to get off local Vision-tier inference, which competes with the main conversation model for the same one GPU and was laggy even with a clean run. `describe_image()` exposes `allow_local_fallback` and `skip_cloud` flags for callers that already know something about current VRAM/cloud state (see `screen_watcher.py`'s use of these — documented further in `08_ui_and_vision.md`); both flags exist because of confirmed live bugs where the *wrong* default (always-skip or always-retry) produced a 19+-hour-stale screen-context cache or a doubled cloud timeout respectively.

`thinking_signal_text` matters for Vision specifically: `screen_watcher.py`'s real prompts are always a long templated wrapper regardless of what the user actually asked, so measuring `prompt`'s own length made the thinking-gate fire on nearly every call — `llm_client.describe_image()` passes the *raw user question* as `thinking_signal_text` instead, so the length threshold measures what it's meant to measure.

## Idle model unloading (`Core/utils/model_lifecycle.py`)

FRED runs continuously (log-on to shutdown), so resident-model VRAM/RAM cost matters even when idle. `ModelLifecycle` is a single watchdog thread (30s tick, `MODEL_WATCHDOG_TICK_SECONDS`), not a per-turn timer — deliberately, to avoid cancel/reschedule churn and timer leaks. A waterfall, each stage gated on the previous one having *already* been unloaded for its own grace period, not on wall-clock idle alone:

1. **LLM** unloads after `LLM_IDLE_UNLOAD_SECONDS` (1 hour) of no use. Measured reclaim: 4566 of 4814 MiB (the ~248 MiB left is the CUDA context, reused rather than leaked on the next load).
2. **Whisper** unloads `WHISPER_UNLOAD_AFTER_LLM_SECONDS` (15 min) *after the LLM specifically* went, not after 1h15m of pure idle — i.e., it waits for the LLM to have been gone a while first, since it's the more expensive one to reload (2.9s vs 1.9s) and the one needed soonest after a keypress. Measured reclaim: 1072 MiB.
3. **Kokoro** unloads `KOKORO_UNLOAD_AFTER_WHISPER_SECONDS` (15 min) after Whisper. Verified: `kokoro_onnx` hardcodes `CPUExecutionProvider` and this environment's onnxruntime has no GPU provider installed — unloading Kokoro frees ~340MB of ordinary RAM, not VRAM, a different and much less scarce resource. Wired in mainly for consistency (so a phrase-cache-only session doesn't hold it resident for no reason), not because RAM was actually tight.

**Reload cost is mostly hidden**: `ModelLifecycle.preload()` fires on the hotkey *press*, concurrently with the user speaking, not after they finish — audio capture needs no model, so recording starts instantly regardless, and only an utterance shorter than the reload time can outrun it. Notably, the LLM is the *one* exception to "preload unconditionally": since the cloud cascade is tried first on every real call, eagerly loading ~9GB of local GGUF onto the GPU on every hotkey press would be dead weight whenever the cloud path is going to answer anyway — `preload()` only eagerly loads the local LLM if a quick connectivity check (`socket.create_connection(("1.1.1.1", 53), timeout=1.0)`) says the machine is currently offline, and that check runs on the background preload thread so a slow/hanging network can never delay the "start recording" return.

## Embedding model (shared across memory, vault retrieval, and tool routing)

`EMBEDDING_MODEL_PATH` = `Qwen3-Embedding-4B-GGUF` at `Q4_K_M`. Upgraded from a `Qwen3-Embedding-0.6B` model (MTEB ~64) after that smaller model's ranking failed to surface a real, relevant vault file for a real query (scored -0.002 to -0.141 centered cosine — see `04a_orchestrator_core.md` for the full incident). 4B (MTEB ~69) chosen over 8B specifically because this model runs **synchronously on CPU, uncached, up to 3x per turn** (memory retrieval, tool routing, vault routing all use it), so inference speed matters as much as ranking quality. Q4_K_M chosen over Q8_0 after a side-by-side test against the real vault showed negligible quality loss (same #1/#2 ranking every time across 3 calibration queries) for half the disk/VRAM (2.5GB vs 4.28GB). **Any embedding-model swap invalidates every cached vector** — FAISS memory indexes self-heal on dimension mismatch, but the vault router's `chunks.json` cache trusts a content-hash match regardless of which model produced the stored vector, so it must be deleted by hand after a swap or it will silently mix old- and new-model vectors.

## Temperature / sampling

`TEMPERATURE = 0.2`, `TOP_P = 0.9`, `MAX_TOKENS = 4096`. Low temperature deliberately, for repeatability ("the same question should get the same answer... what makes an assistant feel dependable"), with an explicit caveat in the comment: **do not expect this to meaningfully affect accuracy** — measured across 3 arithmetic tasks x 8 samples, 22/24 correct at temperature 0.5 vs 21/24 at 0.2, a one-trial difference (noise), despite a smaller run *looking* like a large effect purely by chance (5/6 vs 3/6 vs 2/6). Reasoning quality on the local tiers is bounded by the model, not by sampling. `MAX_TOKENS = 4096` is generous headroom specifically because reasoning-capable models (Nemotron/R1-style) emit a full `<think>` block before the real answer, and too low a limit cuts them off mid-thought, leaking raw reasoning to the user instead of the final answer.
