# Mark I memory system: how it works as a whole (2026-10-03)

Written as if everything were connected to FRED. Today the parts exist and pass their own tests, but nothing in FRED feeds them yet (that is the last step, "integration"). Each part has a plain-words version first, then the technical one.

## The big idea, in plain words
FRED should remember your life the way a good assistant keeps a diary and a filing cabinet.
- **Diary:** every day, write down what happened.
- **Filing cabinet:** keep facts organised, who you know, what you work on, where things stand.
- **Shoebox:** keep the original, untouched record of everything, so nothing is ever lost.
- **Librarian:** find the right memory when asked, even if you word the question differently.
- **Night editor:** every night, read the day, update the diary and the cabinet, and note anything that looks wrong or unclear.

A rule runs through all of it: **nothing is overwritten or deleted.** When something changes ("I moved from Delhi to Pune"), the old fact is marked "true until then" and the new one starts. So FRED can answer both "where do I live?" and "where did I live in March?".

## Parts

### 1. Raw archive (the shoebox) - `archive.py`
- **Plain words:** a record of everything exactly as it happened: conversations, tool use, what was heard, errors. Each day gets its own folder. It only ever adds to the record. It can check itself and tell you if anything went missing or was altered.
- **Technical:** append-only JSONL files per UTC day and stream, plus files stored by content hash (identical files are kept once). An index in SQLite lets `verify()` compare line counts. Stream names are validated, which blocks path-traversal tricks. Historical imports are labelled so they are never mistaken for live data.

### 2. Memory database (the filing cabinet) - `store.py`, `manager.py`
- **Plain words:** the organised facts. Things (people, projects, goals, places) have changing details. Events are notable things that happened. Every entry remembers its source, so you can ask "how do you know this?". `Memory(root)` is the one handle FRED holds to all of it, and the data lives outside the code repo because it is personal.
- **Technical:** SQLite with `entities`, `entity_states` (full history with `valid_from/valid_to`), `events`, `sources` (provenance) and `daily_logs`. One shared connection behind one lock, so several threads can write safely. A broken add-on hook can never lose a saved event.

### 3. Smart search (the librarian) - `semantic.py`
- **Plain words:** finds memories by meaning, not exact words. Asking "when did I start the voice project?" can find a note that says "began working on FRED's speech".
- **Technical:** each event gets a vector from an embedder (injected, not chosen yet), stored per model so swapping models never mixes incompatible vectors. Recall is brute-force cosine similarity in numpy, fine up to about 100k events. `sync()` backfills anything missed, so the index cannot drift from the events.

### 4. Daily consolidation (the night editor) - `consolidate.py`
- **Plain words:** each night, an AI reads the whole day and produces: a short diary entry (short on boring days, longer on busy ones), key events, updates to project facts, new relationships, and two "check later" lists: things that seem to contradict what was known, and questions it could not answer. If the AI gives a bad answer, that day is retried the next night. Running it twice never duplicates anything.
- **Technical:** one LLM call per day returns JSON; results are written with a `consolidation` source. `consolidation_runs` makes it idempotent and records failures; `review_queue` holds contradictions and open questions for the weekly agent. The model is injected (`llm(prompt)->str`). The scheduler is just `run_pending()` on a timer.

### 4c. Field names, optional fact check (2026-10-05) - `consolidate.py`
- **Plain words:** the night editor now reuses the label already used for a fact about someone (so a new coffee opinion replaces the old one and a clash can be seen instead of being filed under a new label). A near-synonym label on the same person is mapped by code; labels are never merged across people. An optional second pass (off by default) re-reads each stored fact about the people mentioned that day: a change of mind updates the fact with history, a real clash goes to the review list. In tests it only caught 1 of 3 planted contradictions, so it stays off.
- **Technical:** `_field` (embedding cosine >= `FIELD_SIM` 0.85, injected `embed`, default no-op), `_check`/`_apply_checks` behind `consolidate_day(check_llm=)`; a recurrence inference needs events in two calendar months at least 7 days apart (`weekly._recurs`); `Week.cands` (default off) adds code-built recurring candidates to the weekly map.

### 4b. Long days and backfill of imported history (added 2026-10-05) - `consolidate.py`
- **Plain words:** a very long day is no longer cut off: it is read in parts, and nothing is saved unless every part came back valid, so a day is never half-recorded. Old chats imported from before FRED stay untouched by default because their dates cannot be trusted. When you tell FRED "the dates between X and Y are right", FRED reads those old days too, oldest first, and files them as history: it does not compare them with how things are today, it does not raise contradictions, and it never overwrites newer facts (an old "phase 1" slots in before today's "phase 3" instead of replacing it). If an old day also has live data, the old summary is added under the live one. The weekly and monthly reviews then pick those old weeks and months up like any others.
- **Technical:** `_chunks()` splits at line ends at `MAX_CHARS`; every part is parsed and checked before `_apply()` writes anything. `trust_dates(mem, since, until, note)` stores ranges in `backfill_trust` (never called automatically); `backfill_pending(mem, llm, model)` runs `consolidate_day(historical=True)` for archive days inside a range (run key `day#backfill`, source kind `backfill`, prompt gets names only, contradictions skipped). Live consolidation ignores `backfill` events. `store.set_state` slots a fact dated before the current one into history (`_set_past`) instead of closing the current value.

### 5. Relationship graph (who and what connects) - `graph.py`
- **Plain words:** a map of connections with dates: "Priya works on FRED, since January", "lives in Pune, since June". Some connections can only have one value at a time (where you live), others can have many (people you know). If a new fact contradicts the timeline, it is not forced in. It goes to the review list.
- **Technical:** `relationships` (subject, relation, object, validity range, confidence, source). `EXCLUSIVE` relations close the previous row when a new one arrives. `path(a, b, at, max_hops=4)` finds the shortest chain of links between two entities (also a tool for the analysts: `find_connection`); `merge` journals every row it moves (`merge_moves`) so `unmerge(entity)` puts everything back; `neighbors(entity, at=date)` answers "who was linked at that time", `history(a, b)` shows how a link changed.

### 6. Name matching (spelling the same person two ways) - in `graph.py`
- **Plain words:** speech-to-text may write "Priya" one day and "Preeya" the next. FRED treats clearly-the-same spellings as one person and remembers both spellings. If it is only maybe the same, it asks you instead of guessing, because merging two real people is worse than keeping one split. A mistaken merge can be undone because nothing is deleted.
- **Technical:** `resolve(kind, name)`: alias or exact match (case and spacing ignored) -> similarity >= 0.85 on raw and phonetic-ish forms (auto-alias) -> >= 0.65 (new entity plus a review question) -> new. Same kind only. `merge()` moves rows and marks the old entity merged.

### 7. Hybrid search and tidying (added later 2026-10-03)
- **Plain words:** search now uses two methods together: meaning (finds "began working on speech" for "started the voice project") and exact words (finds the name "Priya" even when meaning-search stumbles). To stop clutter, only meaningful things become events, repeats are skipped, and old unimportant things are shelved ("cold"): hidden from normal search but not deleted, and brought back if asked for again. Stale questions and shaky connections also expire.
- **Technical:** FAISS flat index (cache) over SQLite vectors + FTS5, reciprocal rank fusion; `hygiene.py` write gate, cold marking, review expiry, weak-link closing. Thresholds are knobs to tune with real use.

### 8. Judged recall (added later 2026-10-03)
- **Plain words:** after searching, the model reads the top 20 results and throws out the useless ones. If nothing useful is left, it searches again more widely using its own better wording and includes shelved memories. If that still fails, FRED asks you for a name, date or keyword instead of guessing. While it searches harder, the talker tells you ("digging deeper...") so you are not left in silence.
- **Technical:** `recall.py` `judged_search`: judge pool, one wider retry (rephrasings, cold included), then an `ask`. Only kept events are marked recalled. A bad model answer falls back to the plain top results.

### 9. Tags and nicknames (added later 2026-10-03)
- **Plain words:** every memory is tagged with who or what it is about. So asking "What's Pri's favourite colour?" works even though the note never says "Su": FRED pulls everything tagged with Priya. If you use a nickname FRED does not know yet, it asks "Do you mean Priya?" and remembers your yes. It never assumes, and if two names fit, it doesn't guess.
- **Technical:** `event_entities` tags written by the nightly run, `Graph.find_in_text` (alias/exact = found, unique capitalised prefix = ask), `events_about`, `confirm_alias`; `judged_search(graph=...)` merges tagged events and saved facts into the candidates.

## How a day flows through it (once integrated)
1. During the day, everything FRED sees and does is written to the **archive**, and important things become **events** (searchable by meaning).
2. At night, the **night editor** reads the day plus what is already known, and updates the diary, facts and connections. Anything doubtful goes to the **review list**.
3. Later, when asked a question, FRED can **search** by meaning, look up **current facts**, check **who connects to whom at a given time**, or read the **diary** for a day.

### 10. The weekly analyst (Phase 5, built 2026-10-04) - `weekly.py`
- **Plain words:** once a week a stronger model reads the week like an analyst. It first gets a one-page map of the week (what topics came up, what changed, what is still open, and which earlier week this resembles). Then it investigates by searching memory for evidence for and against its own guesses, and keeps, weakens or drops each guess. Each guess is saved with the exact memories that back it, so FRED can always say why it believes something. It also rules on the "check later" pile: differences that are only circumstance or a real change of mind are closed, genuine contradictions are kept for you. At the end it writes a short weekly digest that you can ask for. Guesses about personality (traits, values, motivations) are only kept as hypotheses: they need at least two memories behind them, are capped at modest confidence, never reach "supported" from a single week, and never appear in the digest. They grow into something FRED relies on only after showing up week after week, and FRED never recites them or asks you about them: they quietly shape how it answers.
- **Technical:** tool loop, one JSON action per turn, 14 memory-only tools written directly into the system prompt (no embedding tool router, since there are only a dozen), week map from FAISS clusters, `inferences` + evidence + alternatives + change log, `support_weeks` gate, hard call cap with a fallback digest, idempotent per week, runs on the local gpt-oss-20b through an injected `llm(messages)`. Design: `2026/10/04/phase5_weekly_agent_design.md`.
- **Still open:** more specific tools for the consolidation models are to be decided in the final phase.

### 11. The personal model (Phase 6, built 2026-10-04) - `personal_model.py`
- **Plain words:** a short list of things FRED has learned about you: priorities, how you work, habits, preferences, patterns in your decisions. Each item is backed by evidence and is only added once it has held up long enough. Small and obvious things take a week, most things about four weeks, and big claims about who you are (traits, values, motivations) take about eight. If later evidence turns against an item, it is shelved. FRED does not recite this list or put it in every answer. Only when what you say is close to an item does it quietly get added to what FRED considers for that reply. If you ask to see it, FRED shows it, and if you say something is wrong, your version replaces it, is locked, and the guess behind it is dropped for good. It is refreshed lightly every week and rebuilt more thoroughly every month.
- **Technical:** `model_items` (+ log, versions, embeddings), a code gate (tier weeks 1/4/8, 2+ supporting events, counter-evidence at most a third of support) that no model decision can bypass, batched JSON wording call, light/full update modes, demotion by code, `relevant(text)` via embeddings (cut-off 0.45, top 3, nothing when nothing is close), `show/correct/add/remove`. Design: `2026/10/04/phase6_personal_model_design.md`.

### 12. Monthly and yearly reviews (Phase 7, built 2026-10-04) - `period.py`
- **Plain words:** on the 1st of each month FRED reviews the month and asks what really changed: it compares how things stood at the start with how they stand at the end, marks turning points, and keeps a timeline of named chapters of your life ("FRED v2 build, Sep-Oct 2026"). Life runs in parallel, so chapters sit on separate tracks (a big project, social life, school...) and several can be open at the same time. Your own chapters are locked. On your yearly anchor day it looks at the whole year in stages: a short note for each of the twelve months, then one review of the whole year (phases of the year, what stayed the same, what changed, goals dropped or revived), then a critic that argues against that review, weakens anything the evidence does not support, and also looks for what the review missed, for example something from March that comes back in August without anyone connecting the two (it may add a few such findings, with evidence from at least two different months). Old imported history is not mixed in, because its dates cannot be trusted.
- **Technical:** `Month`/`Year`/`Critic` subclass the weekly tool loop; tables for chapters (one open at a time), turning points (need real events), year notes, period runs and digests; resumable yearly run; the anchor sits in the private DB settings. Design: `2026/10/04/phase7_monthly_yearly_design.md`. A full summary of everything through Phase 7 is in `2026/10/04/summary_through_phase7.md`.

### 13. Backups (added 2026-10-04) - `backup.py`
- **Plain words:** you can back up all of FRED's memory, or just one part (the raw archive, the connection map, the diary, the personal model, and so on). Each part comes out as an exact copy that can be restored plus a readable Markdown version, and then the format that suits it: a PDF that opens anywhere for most parts, but a picture (PNG) for the relationship graph (people, projects and places as a node-and-arrow drawing, ended links dashed) and for the life chapters (a timeline with one row per track). You can choose the formats per part. A backup lands in its own dated folder and is never written over, a checker confirms nothing in it changed, and it refuses to be saved inside the code repository because it holds personal data. Backups can also be **encrypted** into one single file that nothing can read without the password (a wrong password, a damaged file or a cut-off file are all detected; the password is never saved anywhere, so if it is lost the backup is gone). A backup can be **restored** into a fresh empty folder, from the normal folder or from the encrypted file: FRED first checks that nothing in the backup changed, never touches a memory that already exists, and only puts the new one in place once its checks pass. A **schedule** function makes a fresh full backup when the newest one is older than a chosen number of days (weekly by default); the timer that calls it is part of the integration step. After each scheduled backup only the newest few full backups are kept (eight by default) and older ones are removed; part backups and anything else in the folder are never touched. You choose per backup whether to encrypt it: a plain backup (the default) needs no password. You can also put back just one part (say the diary or the connection map) into a running memory: missing entries come back, nothing is deleted, entries that differ are reported and only replaced if you say so. Backups go to a folder outside the project (`FRED_Backups` in your home folder by default).
- **Technical:** `backup(mem, out_dir, parts, since, until, pdf, blobs)`; native `.json` / byte-identical archive `.jsonl` + blobs / SQLite online-backup snapshot; `.md` complete; `.pdf` via fpdf2, capped; `manifest.json` with SHA-256 per file and `verify_backup`; `.partial` folder renamed on completion; CLI included. `backup(..., password=)` tars the finished folder and seals it as `<name>.fredbak`: AES-256-GCM in 1 MiB chunks (nonce = random prefix + chunk index, AAD marks the last chunk, so reorder/drop/truncate fails), key from scrypt (n=2^15) of the password, `cryptography` package. `verify_backup(path, password)`, `restore(src, dest_root, password)` (verifies manifest, needs the `database` part, builds `<dest>.partial`, sqlite integrity check, renames; refuses a non-empty destination; whole-memory only), `last_backup`, `run_backup_pending(mem, out_dir=None, every_days=7, password=None, today=None, keep=8)` (prunes with `prune_backups`), `restore_part(mem, src, part, password, overwrite)` (table parts: insert missing rows by primary key, differing rows reported or updated with `overwrite`, FK check after; archive part: add missing day files and blobs, extend a shorter copy, conflicts reported; `database` refused), `DEFAULT_BACKUP_DIR`. CLI: `restore`, `verify`, `scheduled`, `--encrypt` (password from `FRED_BACKUP_PASSWORD` or a prompt, never argv).

### 14. Deep self-analysis (Phase 8, built 2026-10-05) - `selfanalysis.py`
- **Plain words:** when you ask, and once every quarter, FRED reads the whole of its memory and writes down what it understands about you that you may not see yourself: cycles, gaps between what you say and what you do, blind spots. Every statement is sorted into one of four kinds and never blended: what the events plainly show (evidence), a reasoned reading (inference, with how sure it is), things that conflict or are too thin (uncertain), and an openly labelled guess (speculation, which FRED never uses afterwards). Anything it claims must point at real remembered events, and a reading needs events from at least two different days. The strong readings are added to what FRED quietly knows about you (you can correct or remove any of them); the report itself is only shown when you ask.
- **Technical:** `SelfAnalysis(Year)` read-only tool loop over all memory (4x the weekly call cap), write tools refused, `finish(summary, claims)` validated in code (section, event ids exist, inference needs 2+ days and confidence <= 0.8, speculation <= 0.3, bad claims returned once then dropped); tables `self_analyses`, `self_claims`, `self_claim_evidence`; `run_selfanalysis` (request) / `run_selfanalysis_pending` (quarter end, idempotent); `promote` -> `PersonalModel.add_analysis` (source `analysis`, confidence >= 0.5, counter <= 1/3 support); `latest_report` returns only `done` reports.

### 15. Yearly alerts (built 2026-10-05) - `alerts.py`, `gen_calendar.py`, `calendar_india.json`
- **Plain words:** FRED keeps a list of dates that matter to you: birthdays, anniversaries, small memories, and the big festivals, plus one to three fun or unusual days each month (for example India's National Science Day on 28 February). When one is coming up FRED can mention it, with a heads-up of a day or two. Your own dates are kept only in FRED's private memory, never in the code. Dates you were not sure of are saved as unsure and FRED asks you once to settle them. Anything FRED suggests by itself is only a suggestion until you say yes. Moving festivals (Holi, Navratri, Diwali, Eid and so on) are worked out per year from a calendar file; leap day shows up only in leap years, and a birthday on 29 February is shown on 28 February in other years. Nothing is ever deleted: a removed or rejected date stays on file.
- **Technical:** `yearly_alerts` + `alert_log` in the private database; `add` (source user = active, model = proposed), `confirm`, `reject`, `remove`, `fix_date`, `pending` (proposed or unsure), `due(mem, today, ahead)` (personal active alerts + public days; items carry `days_away`, `important`, `certain`, `note`, `age`), `load_seed(mem, path)` for the personal list kept in a file outside the repo, `oldest_date(folder)`. `calendar_india.json` is generated by `gen_calendar.py` (needs the `holidays` package only for generating; covers 2026-2035; the package's gaps (Navratri start, Raksha Bandhan, Ganesh Chaturthi, Maha Shivratri 2026) are filled with dates web-checked on 2026-10-05 for 2026-2030 where several sources agreed; Dhanteras, Bhai Dooj, Onam and other tithi-based days are not covered).
- **January recompute (rule from Vatsal, 2026-10-05):** only the movable days (Diwali, Holi, Navratri, anything lunar; never the fixed ones) are recomputed every year between 1 and 31 January. `run_alerts_pending(mem, fetch, today)` calls the injected `fetch(year)` (web search, panchang page or the holidays package: the integration chooses) and `recompute_year` stores the answer in `alert_calendar` (old rows kept with `current=0`); `due()` then prefers those rows over the JSON. Idempotent per year, at most one try a day, catches up if January was missed, an empty or failed fetch never wipes anything (recorded in `alert_refreshes`; from 31 January a failure also adds a review-queue question). The result lists the unsure alerts FRED should ask about (`to_ask`). Chain it after the yearly review on Vatsal's birthday (24 January, inside the window) and from the daily timer. FRED's own birthday is stored as 16 Sep 2025 (Vatsal: first local model downloaded that day; naming and idea formed late Aug to early Sep, only the 16th is used).

### 16. Curation tools and proposals (built 2026-10-05) - `memtools.py`, `maintenance.py`, `schema_maintenance.sql`
- **Plain words:** a new set of tools for the memory agents themselves (nothing to do with what FRED uses when talking to you). They look after the quality of memory: duplicate or confused people and things, wrong nicknames, facts gone stale, claims with no source, holes in the record. The agents work in the background and cannot wait for your answer, so they only PROPOSE. There are two tiers. **Auto:** a merge the agent is very sure of (confidence 0.9 or more, same kind of thing, at most three per run) is applied at once because merges can be undone; it is listed in the next report so you can say "undo". **Ask:** everything else waits. FRED raises waiting proposals in conversation, a couple a day, each at most twice, and your yes or no applies or closes them; or you go through them with `python maintenance.py review <memory folder>`. Unanswered proposals do nothing and wait as long as it takes; they never expire. Something you rejected stays on file (you can list them) and is never proposed again. Nothing is deleted: a split moves tags (undoable), a retired nickname is kept on file, a stale fact only gets an end date.
- **The 14 tools (`memtools.py`, a mixin of the tool-loop engine, so every agent can use the read-only ten):** `source_check`, `find_contradictions`, `confidence_audit`, `coverage_gaps`, `timeline_gaps`, `dedupe_events`, `orphan_report`, `backup_status`, `queue_summary`, `decision_replay` (read-only, in every agent's prompt) and `propose_merge`, `propose_split`, `retire_alias`, `flag_stale` (proposals; only the critic and the maintenance agent, others get "may not propose").
- **Technical:** `proposals` table (kind merge|split|retire_alias|stale_fact, payload JSON, reason, confidence, tier, status proposed|applied|confirmed|rejected|undone, asks, last_asked, reported), `retired_aliases`, `maintenance_runs`. API: `propose` (validates ids, refuses duplicates and rejected repeats, applies only the auto tier), `confirm`, `reject` (undoes an auto-applied one first), `undo`, `answer(mem, id, yes)`, `pending`, `history(mem, status)` (everything ever proposed, e.g. only the rejected), `ask_next(mem, limit, today)`, `report`, `review` (command line yes/no/skip). The maintenance agent (`Maintenance`, a tool loop with a map of queues, backup, coverage, orphans, confidence audit and recent proposals) runs via `run_maintenance` / `run_maintenance_pending` (weekly, idempotent per day). All proposals and applications go to the decision log. The proposals (waiting, applied, confirmed, rejected) and retired nicknames are in the backup's `review` part (readable md/pdf and restorable with `restore_part`) as well as the full sqlite backup. Self-check: `python maintenance.py`. Integration chains `ask_next` into the conversation, `report` into the digest and `run_maintenance_pending` into the timer.

### 17. The ask queue (built 2026-10-06) - `askqueue.py`
- **Plain words:** every doubt that needs you (same-person questions, contradictions, merge and other proposals) waits in one queue and is asked as an either/or when a conversation winds down: "Quick one, sir: Nitu (came with me to tuition yesterday) and Nitya (lives in Pune). Same one, or two different ones?" Each side is described, so the answer is a pick. Short chats rarely trigger it, longer ones more; one question per conversation end, at most 5 a day, each item at most twice, "ask me later" snoozes it 3 days, and the item closest to what you just talked about goes first. Your answer closes it everywhere and is written to the archive, so the nightly editor sees it. Delivery (FRED speaking it, the pill popup with a text box, the HUD) and the "conversation is ending" signal are integration work. 
- **Technical:** `ask(mem, topic, turns)` and `answer(mem, id, reply)` over the `ask_state` table; replies accept the option key, a letter or a plain word; a "same one" answer on a review question becomes a merge proposal (undoable, a "no" is never proposed again).

### 17b. Two projects fit one question (built 2026-10-06) - `recall.py`
- **Plain words:** "when did I start the voice project?" when both a voice assistant project and FRED's voice exist: FRED answers about both ("groups") and then offers a question ("That fits Voice Assistant and FRED Voice. Did you mean one of them in particular?"). If you say "fred" in the question, FRED's projects are listed first, but nothing is filtered out, because not every "fred" means a FRED project.
- **Technical:** `_by_project` groups the kept events by tagged project entities; 2 or more projects gives `groups` and `follow_up` on the `judged_search` result.

### 17c. Precedents (decision memory, built and tested 2026-10-06) - `precedents.py`
- **Plain words:** when you settle a doubt, FRED keeps what kind of case it was and what you chose. When a near-identical case comes again, FRED first suggests your usual answer ("I'd say 'two different ones', like your 3 earlier answers"), and after you keep agreeing it settles such cases itself, tells you in the digest, and `undo` reopens one (that also lowers its confidence in that kind of case). It never settles when the earlier answers disagree, when the model sees something new in the case, or for high-stakes kinds (contradictions are only ever suggested). Reasons are only your own words or "none"; FRED never invents one. A choice made repeatedly with reasons becomes a line in the personal model. Details and measurements: `2026/10/06/done.md`.
- **Technical:** tables `precedents`, `autonomy`, `precedent_use`; `record`, `decide`, `outcome`, `reason_tags`, `distill`; `askqueue.settle/report/undo`; default model gpt-oss-20b at low reasoning.

## Review hardening (2026-10-05, after an adversarial code review by a larger model)
- **Plain words:** an independent review found 27 problems; the serious ones are fixed. Odd characters or a half-written line in the archive can no longer stop nightly consolidation and backups (they are skipped and reported by `verify()`); a bad or hostile timestamp can no longer write files outside the archive, and every time is stored as UTC; an old imported fact can no longer overwrite something you confirmed later (it becomes a review question); similar-looking names (Manish/Manisha) are asked about instead of silently merged; a nickname that already belongs to someone cannot be re-pointed by a model; a merge you rejected or undid is not redone, in either direction; the weekly analyst always sees every section of its map; the support-weeks count needs genuinely new evidence; a night with a malformed answer writes nothing and does not duplicate questions; the personal model keeps removed items removed; encrypted backups no longer leave readable staging files in the backup folder; and backups no longer freeze the memory while they build PDFs.
- **Technical:** `archive.parse_lines` (split on newline only, bad lines skipped and counted), `Archive.write` repairs a torn last line, `store.to_utc` at every write entry point (naive times refused), `entity_states.last_seen` and `relationships.last_seen` (re-confirmation time) with `store.ensure_column`, `graph._variant` (strict automatic alias), `Graph.add_alias(..., force)` plus journaled closes in `merge` (no self-loops, undo reopens only when nothing newer is open), proposals keyed by the unordered pair with `undone` blocking auto-apply, `consolidate._valid` (whole answer checked before any write) and `_pick` (entity list capped), per-section budget in `Week.week_map`, `update_inference` counts a week only for new in-week evidence, a `real` ruling is never overwritten, `run_weekly/monthly/yearly(force=)` and incomplete runs count as finished for the timer, incomplete yearly drafts are not kept, `add_analysis` honours removals and corrections, semantic index appends instead of rebuilding, `backup()` snapshots under the lock and renders outside it and stages encrypted backups in a temp folder, `restore_part("archive")` appends only the missing tail under the lock. Each fix has an assertion in its module's self-check.
- **Synthetic year and the oracle run (`run_synthetic.py`, `testdata/synthetic_year/`):** 120 days of invented conversations (a fictional 15-year-old, all names made up) with an answer key (`truth.json`) holding 16 kinds of planted trap: aliases and misspellings, similar-name pairs that must not merge, changing and out-of-order facts, real and apparent contradictions, true patterns and decoys, relationship changes, decisions, chatter the write gate should skip, near-duplicates, prompt injections, sarcasm, hypotheticals, trait talk, and spoken corrections. `python run_synthetic.py` feeds the days through the real pipeline with the key's own extraction answers standing in for the model, and scores what the CODE does with them: all 116 non-empty days consolidate, aliases resolve to one entity (8/8), different people stay separate (3/3), fact timelines end on the latest value (6/6), and injected, sarcastic, hypothetical, trait and chatter lines are not stored as facts (all). It found one real flaw: the strict name rule from the review fix still auto-merged names one letter apart (Pranay/Pranav), so `_variant` now only auto-aliases pure spelling variants (phonetic twins, or names that differ only by h and doubled letters, e.g. Nitya/Nithya); a one-letter difference is asked about. Checks that need a real model (patterns, contradiction rulings, decisions, trait caps) are for the local-model run.
- **First runs on the real local models (Qwen3-8B nightly, gpt-oss-20b for the rest; `run_local.py`, 2026-10-04):** the answer-key harness only proves the code, so the models were run on slices of the synthetic year and each stage was judged by a separate agent against the key. The nightly output was noisy at first (topic nodes as entities, FRED's own explanations as events, a review queue that was about 90% noise), so the nightly prompt and a cleanup step were tightened: the user is named, entity kinds are limited (person, place, project, pet, org, task, goal), relations come from a fixed list with the direction spelled out, a state is never a relative time ("tomorrow"), one open question a day, a contradiction must quote the stored fact it clashes with. The weekly agent finished at the first chance, found no patterns and saw events and review items dated after its own week; the monthly agent never recorded its turning points. Fixes in the shared engine: every tool stops at the period end, finish is refused until every open review item is ruled and the agent has explored (3 search/compare calls weekly, 2 monthly), the monthly agent must record turning points and chapters, "real" is only allowed on contradiction items, repeating a ruling is harmless, and the review counts and the "Please check" list are written by the code, not the model. gpt-oss only answers inside a forced JSON format on LM Studio, so the runner passes a JSON schema per call type.
- **Verification night, what the analyst agents can and cannot do (2026-10-05, answer-key harness, gpt-oss-20b):** the machinery is safe (nothing after the period end leaks into the agent's view, evidence ids must have been shown to the model, the review footer and the turning-point list are written by the code, the same call twice is refused, finishing is refused until the open review items are ruled). Accuracy is not there yet: after four weekly iterations the agent still closed three of five real contradictions as "historical_change" and found one of six true patterns; monthly records turning points with correct evidence but no chapters and no new patterns. Other models tried (Gemma 4 12B, Qwen3.5-9B, K2 Horizon 7B) were not better within the time caps; details in `Documentation/2026/10/05/model_comparison_2026-10-05.md`. Open decision for Vatsal: let the user alone close contradiction items.
- **Spoken name corrections:** the nightly output has a `corrections` list (`wrong`, `right`). The code applies one only if both names are in what was actually said that day. `Graph.correct()` merges the entity named `wrong` into `right` (journaled, `unmerge()` undoes it), renames the old entity ("Navya [heard as Nitya]"), retires the word so it can later name a different person (a real Navya in the tuition class), and re-points a word that was only an alias. The synthetic key now includes the 21 Jan correction, and the harness checks that the early "Navya" events belong to Nitya afterwards.
- **Left as they are (known, low risk):** `unmerge` still deletes the merge journal rows; hygiene still gives weak links an end date; every weekly/monthly run builds a second FAISS index of past vectors; `verify()` detects lost, extra or torn lines but not an edit inside a line; an alias is not yet required to appear in something the user said that day.

## Decision log (built 2026-10-05) - `decisionlog.py`
- **Plain words:** the small models make many decisions, so FRED keeps a detailed diary of them in its private database (never the code repository): everything a model was asked, what it answered, every tool it used with the result, every time the code refused or overruled it (a rule about evidence, a quality gate, a refused action), and every time its answer was unusable. If a model ever reaches a wrong conclusion, you can replay exactly how.
- **Technical:** one `decision_log` table (`at, agent, run, kind, data` JSON), kinds `prompt | reply | action | override | model_failure`; written by `note()` (never raises), `traced()` wraps the prompt-style model sockets (nightly consolidation, recall judge, personal model), the tool loops (weekly, monthly, yearly, critic, self-analysis) log inside `Week`, and code overrides are logged at the write gate and the personal-model gate; read with `show(store, agent, run, kind, limit)`; included in the sqlite backup. Full text is kept on purpose while the models are still being judged; prune by age later.

## Safety rules built in
- Nothing is overwritten or deleted. Facts get end dates and merges are reversible.
- Every fact keeps its source.
- A bad AI answer or a bad single row never loses the rest of the day.
- Doubt goes to a review list, not into the memory as fact.
- Personal data lives outside the code repo.
