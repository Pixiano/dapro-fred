💡 F.R.E.D. — Ideas & Follow-Ups
(Things noticed during dev/testing that aren't full phases of their own)

From Phase 14 (Hands on the Machine) testing:

- Window management (focus/minimize/maximize) has no dispatcher
  shortcuts yet — only reachable via natural LLM phrasing right now.
  Could add deterministic routes like the volume/brightness ones if
  it turns out to get used a lot.

- Confirmation gate currently treats anything that isn't a recognized
  affirmative ("yes"/"yeah"/"do it"/etc.) as a cancel. Worth living
  with it a bit to see if that feels right, or if it should re-prompt
  on genuinely ambiguous replies ("wait what?") instead of silently
  cancelling.

- launch_application resolves apps by alias map -> PATH -> App Paths
  registry -> install-dir search, but only ever matches an EXACT
  filename. Already bit OBS once (real exe is obs64.exe, not obs.exe)
  before that got added as an alias by hand. A fuzzy/substring match
  in the install-dir search (instead of exact filename equality)
  would catch this whole class of "close but not exact" mismatch
  automatically, instead of needing a hand-added alias every time.

Future idea — contextual app-opening:

  "Hey Fred, open VS Code and the last file I had opened, probably
  settings.py"

  Goal: PC control that isn't just "launch X," but launches X *with*
  context pulled from recent history/memory — last-opened file,
  last project folder, etc. — instead of a bare cold launch.

  Sketch of how this could actually work:
  - Track "recently opened" per-app where the OS/app already exposes
    it (VS Code keeps its own recent-files list; Windows Recent Items
    / jump lists cover a lot of apps generically without FRED needing
    to track anything itself).
  - launch_application gains an optional second step: after the
    process starts, pass a resolved file/folder argument (e.g.
    `code.exe <path>`) instead of just opening the bare app.
  - The "probably settings.py" part of the phrasing is a fuzzy hint,
    not a guarantee — needs graceful handling when the guess is wrong
    or nothing recent is found (fall back to a bare launch + say so,
    rather than failing the whole request).
  - This is squarely an LLM-reasoning task (interpreting "the last
    file I had open, probably X" is fuzzy intent, not a deterministic
    pattern) — belongs in the tool-calling path, not the dispatcher.

Future idea — FRED gets agentic-coding-assistant-style tools/skills (NOT NOW —
revisit after Phase 20, this is a separate project on top of the
roadmap, not a phase in it):

  Goal: give FRED an actual agentic coding loop — read a file, edit
  it, run it, see the error, retry — instead of just generating code
  as chat text. Today FRED's models can write code in a reply (any
  capable LLM can), but there's no read_file-write_file-run_command
  tool trio plus a retry loop wired to act on the results, so there's
  no way for FRED to actually verify its own code works.

  Rough shape of what's needed, when the time comes:
  - read_file/write_file tools already half-exist via machine_tools
    (read_file does; write needs adding — create_text_file overwrites
    blind, no diff/patch concept).
  - A run_command tool (subprocess, captured stdout/stderr/exit code)
    — currently nothing executes arbitrary code at all, on purpose.
  - A loop that feeds command output back to the model and lets it
    decide to retry, distinct from the existing one-shot tool-calling
    loop (_generate_with_tools currently does at most one
    call-results-finalize round, not an iterate-until-done loop).
  - Real scoping/safety questions before this is sane to build:
    arbitrary code execution is a much bigger blast radius than
    anything in Phase 14's confirmation gate (that gate handles "are
    you sure," not "is this code safe to run at all"). Needs its own
    design pass, not a bolt-on.

STT accuracy — Vosk mishearing simple commands:

  Observed: "open notepad" recognized as "north bay", "not bad", and
  other near-misses, repeatedly, never the right phrase. This is the
  STT model itself, not the dispatcher (the dispatcher matched fine
  once it got correct text — it just wasn't getting correct text).

  Why: Core/models/vosk-model-small-en-us-0.15 is Vosk's SMALLEST
  English model (~40MB), built for low resource use over accuracy.
  General-purpose dictation models like this have no bias toward
  short command-style phrases, so a 2-word phrase like "open notepad"
  has very little context to disambiguate against — it's exactly the
  case this model struggles with most.

  Near-term fix (quick, just a config change once downloaded): swap
  to a bigger Vosk model. Real options, not just the 40MB vs 1.8GB
  extremes:
    - vosk-model-en-us-0.22-lgraph  — 128MB, best accuracy-per-MB
      (pruned lookahead graph, not full open dictation)
    - vosk-model-en-us-daanzu-20200905 — 1.0GB, the "middle ground"
    - vosk-model-en-us-0.22 — 1.8GB, the full accurate model

  Longer-term fix: grammar-constrained recognition (a fixed expected-
  phrase list instead of open dictation, for command-style speech
  specifically) — homed in Phase 20 of the JARVIS roadmap now, since
  it's exactly the "make voice reliable for daily use" work that
  phase is already about. See that file for the actual task writeup.

Operating modes (2026-08-14) — not designed yet, just logged so it's
not lost:

  1. General mode — what FRED runs as today, no change needed.
  2. Lockdown mode — BUILT 2026-08-14. Say "lockdown" to engage,
     "unlock" or "stand down" to lift (exact-match, no LLM in the
     loop). While locked, every tool call is refused (gated once
     in ToolRegistry.execute — Core/tools/registry.py — not
     duplicated per tool); conversation still works, FRED just
     can't act on anything. State: Core/state/lockdown_state.py.
     Test: Core/tests/test_lockdown.py.
  3. Friend mode — a general "talking to a friend, not Vatsal"
     mode, possibly with per-friend variants later. Undecided:
     how it's triggered, what changes (persona? memory/vault
     access? tool access?), how per-friend customization works.
     Not started.

Speaker recognition (voice ID) (2026-08-14):

  FRED currently has no way to tell WHO is talking, only that the
  wake word was said. A speaker-embedding model (SpeechBrain
  ECAPA-TDNN or Resemblyzer — both fine on CPU, no GPU needed)
  could enroll Vatsal's voice once, then score every utterance
  against it via cosine similarity.

  Ties directly into the operating modes above:
  - Friend mode trigger: an unrecognized voice auto-switches mode
    instead of needing a manual command.
  - Lockdown mode gate: sensitive commands (vault, PC control)
    could require a voice match, refusing unrecognized speakers
    automatically.

  Ceiling: a voice-embedding check can be defeated by a good voice
  clone — Vatsal literally builds that tool (Project Copy), so this
  is not a real security boundary on its own. Fine as a UX gate for
  mode-switching; pair with something else (PIN phrase, explicit
  confirmation) before trusting it for anything that actually
  matters.

  Not started — revisit once Friend/Lockdown modes get designed,
  since this is the natural trigger for both.

Voice-cloning-adjacent ideas (2026-08-14):

  Separate from Project Copy itself, but same tech family:
  - Paralinguistic/emotion detection from voice (stressed, tired,
    joking) using similar embedding-style models with a different
    head — could let FRED shift tone. Low priority, not urgent.
  - The real intersection point is the anti-spoofing note above —
    Vatsal's own clone-building expertise is exactly the threat
    model any voice-based auth in FRED needs to account for.

Camera / visual feed (2026-08-14):

  Vatsal is open to this — flagged as GPU-taxing but "a very
  interesting and viable idea." Core/vision/ today only handles
  screen capture (screen_watcher.py: separate process, interval-
  gated, skips its cycle if the main process has a model loaded to
  avoid VRAM collision). A camera watcher is the same pattern with
  the frame source swapped, not a new subsystem.

  To keep it cheap:
  - Trigger capture on-demand (wake word / "look at me") rather
    than continuous streaming.
  - For any ambient/always-on version later: gate the expensive
    VLM call behind a near-free classical check first (OpenCV
    face/motion detection, CPU-only), only escalate to the VLM
    when that check finds something.
  - If face recognition is ever needed, reuse the pipeline from
    dapro-drive-face-recognition-plan.md (Drive project) instead
    of standing up a second model.

  Not started — revisit when Vatsal wants to spend the GPU budget
  on it.

  Concrete setup sketch (2026-08-14), reusing the screen-watcher
  scaffolding rather than building a new subsystem:
  - Capture: swap the screenshot grab in screen_watcher.py for
    cv2.VideoCapture(0) grabbing one frame. Same file shape, same
    VLM call on the frame.
  - Keep it a separate OS process, same reason as screen (shared-
    process VLM calls already crashed this codebase once).
  - Reuse the existing GPU-arbitration check (LLM_STATUS_PATH) —
    skip the cycle if the main model is loaded. This is the actual
    mitigation for the GPU-cost concern, already built for screen.
  - Expose as an on-demand tool (whats_around_me(), mirroring
    whats_on_screen()) via capture_now() — triggered by "look at
    me," not a continuous stream or idle-loop watcher, unless
    ambient awareness is wanted later.
  - Needs real hardware: a webcam pointed at Vatsal. Undecided
    whether that's dedicated or an existing one.

  Facial recognition (2026-08-14) — layers on top of the camera,
  requested so FRED can tell Vatsal apart from parents/family/
  friends and let that trigger protocols proactively:
  - Cheap gate before any VLM call: OpenCV/dlib face detection
    (near-free, CPU) decides "is there a face" before spending a
    VLM call on it.
  - Recognition: face-embedding model, enroll faces, cosine-
    similarity match — same shape as the speaker-ID idea above.
    Reuse the pipeline from dapro-drive-face-recognition-plan.md
    (Drive project) instead of standing up a second model.
  - Pairs with speaker ID (voice) as the visual counterpart — face
    match + voice match together feed the same Friend-mode/
    Lockdown-mode trigger and let FRED recognize a specific person,
    not just "someone," for proactive JARVIS-style protocols.
  - Not started, depends on the camera setup above existing first.

Phone integration (2026-08-14):

  Two tiers, deliberately scoped down by Vatsal himself given
  FRED's current track record — only the first is considered
  viable right now:

  1. Remote-control app sending commands to FRED's API — Android
     only ("Apple is a shit ton of work"). Lets Vatsal trigger
     FRED actions (starting with phone calls) from his phone
     instead of only from the PC mic. Needs: an API endpoint on
     FRED's side to receive commands, and an Android app (or
     Tasker/HTTP-shortcut style approach before a custom app) to
     send them.
  2. Full phone control (FRED reads/acts on the whole phone, not
     just placing calls) — explicitly deferred by Vatsal as too
     advanced for where FRED's reliability is right now. Revisit
     only after the simpler call-only version is solid.

  Not started.

Weather forecasts (2026-08-14) — FUTURE half BUILT, past still not
started:

  get_weather(location="", when="") in Core/tools/web_tools.py.
  `when` blank/"now"/"today" is the original current-conditions
  path, untouched. "tomorrow" / "day after tomorrow" pulls a real
  forecast from wttr.in's JSON endpoint (?format=j1) — high/low +
  midday condition. Anything else (further out, or any past
  reference) gets an honest "can't see that far, no historical
  data" reply instead of a guess.

  Past/historical: still not started — wttr.in has no historical
  data, would need a separate free/no-key source, e.g. Open-Meteo's
  historical archive API. Revisit if it's actually wanted later.

  Known limitation, not fixed (pre-existing, out of scope for
  today): the deterministic dispatcher's weather regex greedily
  captures everything after "in/for/at" as the location, so
  "what's the weather in Mumbai tomorrow" (location + day in one
  sentence) is parsed as location="Mumbai tomorrow" and fails
  gracefully ("couldn't find weather for 'Mumbai tomorrow'")
  instead of returning tomorrow's Mumbai forecast. Ask for the two
  separately ("what's the weather in Mumbai" / "what's tomorrow's
  weather") until this is worth a real fix.

  Self-check: __main__ block in web_tools.py itself (not
  Core/tests/ — that folder's README restricts it to regression
  tests pinning a bug that actually happened, and this is new
  logic, not a pinned bug).
